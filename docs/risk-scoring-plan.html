Risk Scoring Engine — chấm điểm rủi ro gian lận giao dịch

Ứng dụng chấm điểm rủi ro (0–100) cho từng giao dịch dựa trên mô hình học máy huấn luyện từ bộ dữ liệu IEEE-CIS Fraud Detection, có API chấm điểm, dashboard xem điểm rủi ro + giải thích SHAP, và luồng rà soát/gắn nhãn thủ công.

Dataset: IEEE-CIS (Vesta) · ~590k giao dịch · gian lận ~3.5% Data · Model · BE · FE An · Quân · Trung · Long

01Mục tiêu & phạm vi rút gọn cho 8 ngày

Với 8 ngày, không làm một hệ thống hoàn chỉnh — chỉ cần chứng minh pipeline chạy được end-to-end với 1 model tốt nhất đã chọn.

Trong phạm vi

1 model duy nhất đã so sánh & chọn (không thử nghiệm dàn trải), API chấm điểm 1 giao dịch + SHAP top-5, dashboard danh sách/chi tiết/rà soát gắn nhãn, Docker chạy local cho buổi demo.

Cắt bỏ hoàn toàn

Đăng nhập/phân quyền (dùng tài khoản demo cứng), retraining tự động & model registry nhiều phiên bản, streaming thật/deploy cloud, bảng theo dõi drift phức tạp — chỉ 1 biểu đồ PR-AUC tĩnh.

03Dữ liệu & mô hình AI

IEEE-CIS gồm 2 bảng nối qua TransactionID: transaction (~434 cột: số tiền, thẻ, địa chỉ, khoảng cách, counting features C1–C14, time-delta D1–D15, match features M1–M9, Vesta engineered V1–V339) và identity (~41 cột: thiết bị, trình duyệt, thông tin định danh). Nhãn isFraud mất cân bằng nặng (~3.5% gian lận).

Hạng mụcQuyết định kỹ thuậtLý do
Xử lý mất cân bằngKhông oversample thô; dùng scale_pos_weight / class weight + đánh giá bằng PR-AUCOversample (SMOTE) trên dữ liệu tabular nhiễu dễ tạo mẫu giả, sai lệch feature V/C
Chia train/validationChia theo thời gian (TransactionDT), không random splitDữ liệu có tính thời gian — random split gây leakage, model ảo tưởng độ chính xác
Missing valuesGiữ NaN cho model tree-based (LightGBM/XGBoost tự xử lý)Không cần impute thủ công, tránh mất tín hiệu "thiếu dữ liệu = rủi ro"
Categorical encodingLabel encoding hoặc target encoding có kiểm soát leakage cho card, ProductCD, P/R_emaildomain, M1–M9Cardinality cao, one-hot sẽ nổ chiều dữ liệu
Thuật toán chínhLightGBM (baseline), thử XGBoost để so sánhChuẩn công nghiệp cho bài toán tabular gian lận, train nhanh, xử lý tốt missing/imbalance
Metric đánh giáPR-AUC làm chính, ROC-AUC phụ, theo dõi recall @ fixed precisionVới lớp hiếm, ROC-AUC dễ "ảo" — PR-AUC phản ánh đúng bài toán rà soát gian lận
Giải thích kết quảSHAP values, trả kèm top-5 feature đóng góp mỗi giao dịchNhân viên rà soát cần biết "vì sao điểm cao" — yêu cầu bắt buộc của bài toán risk scoring

07Rủi ro với lịch 8 ngày

CAO · Không đủ thời gian nếu chờ tuần tự

Nếu Trung chờ Quân xong model rồi mới code API, hoặc Long chờ Trung xong API rồi mới code UI, 8 ngày là không đủ. Bắt buộc làm song song với mock/stub trước — chỉ tích hợp thật vào Ngày 5–6.

CAO · Data leakage do vội

Áp lực thời gian dễ khiến bỏ qua bước chia train/test theo thời gian, dùng random split cho nhanh — dẫn đến số liệu ảo khi trình bày. An phải chốt cách chia dữ liệu ngay Ngày 1–2.

TB · Đóng gói model trễ

Nếu Ngày 5 Quân chưa xong score(), Trung mất nốt thời gian còn lại để tích hợp. Nếu trễ, dùng tạm model baseline (Logistic Regression) để demo pipeline chạy được.

THẤP · Thiếu dữ liệu identity

Bảng identity chỉ khớp được ~24% giao dịch — An cần xử lý rõ trường hợp thiếu ngay từ Ngày 1, không để pipeline lỗi khi thiếu identity.
