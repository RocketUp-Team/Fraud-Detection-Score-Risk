\chapter{Conclusion and Future Work}
\label{chap:conclusion}

\section{Conclusion}

The project demonstrates an end-to-end fraud scoring workflow that separates distributed Spark data preparation from single-node Python model training and in-process API serving. The strongest current challenger, CatBoost Balanced, achieves validation ROC-AUC \val{0.9081} and PR-AUC \val{0.5806}; on the later holdout it achieves ROC-AUC \val{0.8781} and PR-AUC \val{0.4266}. Because holdout PR-AUC is below the required promotion target, the candidate remains \texttt{not\_promoted}. The most defensible conclusion is therefore that the project has produced a coherent and auditable academic demonstration, not a production-ready fraud decision system.

The main lesson is that fraud-risk quality depends on the relationship between
data, time, model, policy, and review workflow. The Spark pipeline protects the
data boundary and produces a reusable contract, while the model workflow
provides a disciplined comparison between candidate families. Calibration,
TreeSHAP explanations, and analyst review make the score more usable, but they
do not remove the need for monitoring and governance. The failed holdout
promotion gate is particularly informative: it shows that a candidate can be
technically valid, explainable, and strong on validation while still requiring
more evidence before becoming the runtime default.

\section{Summary of research question answers}

The answer to RQ1 is positive within the recorded evidence: chronological splits, schema contracts, and the automated verification checks support a leakage-controlled handover. The answer to RQ2 is qualified: CatBoost Balanced obtains the highest validation PR-AUC among the current candidates, but its holdout PR-AUC falls below the promotion target, so validation leadership is not sufficient for promotion. The answer to RQ3 is also positive for the demonstration: the in-process Python package can score requests without a Spark dependency at request time. Finally, RQ4 is answered by the limitations documented in the validation chapter: offline--online feature parity, policy ownership, fallback behaviour, security, and monitoring define the boundary between the current demo and a deployable service.

\section{Future work}

The first priority is to implement a real-time feature store, for example with Feast or a Redis-backed stream-processing layer, so that rolling entity aggregates can be calculated consistently at inference time. The second priority is to separate operational policy from model weights by introducing a dynamic threshold and risk-band service that authorised risk officers can update without redeploying the model artifact. The third priority is to add MLOps controls for population stability, prediction drift, experiment lineage, and controlled retraining when validated performance falls below an agreed service level. A later research direction is to model relationships between transactions, devices, cards, and identities with graph neural networks and temporal sequence models, since coordinated fraud may not be visible in isolated rows. Finally, the analyst experience can be strengthened by extending TreeSHAP with actionable counterfactual explanations that clarify which measurable conditions would change a review outcome.

The recommended implementation order follows dependency risk. Online feature
parity should be addressed first because a stronger model cannot compensate for
features that are calculated differently at serving time. Policy ownership and
audit logging should follow so that decisions are traceable and thresholds can
be changed safely. Drift monitoring and automated retraining should then be
introduced only after the measurement and rollback procedures are stable.
Graph and sequence models are research extensions rather than immediate
replacement candidates; they should be evaluated against the same chronological
holdout and promotion gates. This sequence keeps future complexity tied to
measurable operational benefit.
