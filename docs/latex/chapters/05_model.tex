\chapter{Model Development, Evaluation, and Serving}
\label{chap:model}

\section{Model-development protocol}

The intended training protocol is:

\begin{enumerate}
  \item read \texttt{train\_weighted}, validation, and holdout Parquet;
  \item fit categorical indexers on training only;
  \item apply the frozen indexers to later windows;
  \item select the canonical 68-feature order and convert to pandas;
  \item compare candidate models on validation;
  \item tune the selected tree family on validation;
  \item evaluate the final configuration once on holdout;
  \item save estimator, mappings, feature order, metadata, and SHAP support.
\end{enumerate}

The exclusion of \texttt{split\_name}, processing metadata, identifiers, labels,
and class weights from the model vector is enforced in
\texttt{features.py}. This addresses a prior failure in which the string
\texttt{train\_weighted} entered the numeric training frame.

\section{Tuning}

The documented V2 LightGBM grid is intentionally small:

\begin{lstlisting}
n_estimators: [200, 400]
max_depth: [4, 6]
learning_rate: [0.05, 0.1]
\end{lstlisting}

The saved best configuration is reported as 400 estimators, depth 6, and
learning rate 0.05. A small grid is reproducible and affordable for the project,
but it is not evidence that a broad hyperparameter optimum was found.

\section{Artifact structure and versioning}

The current V2 directory contains:

\begin{itemize}
  \item \texttt{baseline\_logreg\_v2.joblib};
  \item \texttt{final\_model\_v2.joblib};
  \item \texttt{model\_comparison\_v2.json};
  \item \texttt{training\_metadata\_v2.json}.
\end{itemize}

Serving defaults to V2 in configuration. Setting
\texttt{FRAUD\_MODEL\_SERVING\_VERSION=v1} selects the V1 path and supports the
legacy root artifact.

Training and serving targets are separate. This is a sound deployment boundary:
training a new version need not overwrite the served artifact. The remaining
lineage gaps are immutable checksums, external registry location, completed
tracking runs, explicit promotion approval, and rollback smoke evidence.

\section{Request-time scoring}

The scoring module loads one artifact into a process cache and initializes a
TreeSHAP explainer for supported tree families. For each request it:

\begin{enumerate}
  \item checks missing required features;
  \item maps raw categorical strings using training-derived dictionaries;
  \item substitutes the configured missing sentinel;
  \item aligns columns to the training order;
  \item calls \texttt{predict\_proba};
  \item optionally applies a calibrator;
  \item computes the five largest absolute SHAP contributions;
  \item labels the request as full-feature or partial-demo.
\end{enumerate}

This path does not start Spark. It is suitable for a low-latency API process,
although inference latency was not saved as evidence.

\section{Explainability}

For tree models, each response can contain:

\begin{lstlisting}
[
  {"feature": "TransactionAmt", "shap_value": 0.41},
  {"feature": "card4", "shap_value": -0.19}
]
\end{lstlisting}

A positive value pushes the model output toward the fraud class and a negative
value pulls it toward legitimate. The list is local to one prediction and must
not be interpreted as global feature importance or causal explanation.

When a calibrator transforms raw model probability, the current SHAP values
still explain the raw model. A production UI should label this distinction or
use an explanation method aligned to the displayed output.

\section{Risk scoring and operating policy}

The backend maps probability to a rounded score and fixed bands. The model code
contains threshold-analysis and optional threshold metadata paths, but the V2
artifact directory has no calibration/threshold outputs, and the backend does
not use model thresholds as decision authority.

This is the most important distinction between model quality and operational
readiness. Area metrics show ranking quality across thresholds. They do not show
the number of false alerts, missed frauds, or reviewers needed at scores 40 and
80.

\section{Experiment tracking}

The model package implements an MLflow wrapper and declares MLflow as a current
dependency \parencite{mlflow}. The observed local tracking directory contains
experiment metadata but no completed run evidence. Therefore the thesis reports
tracking as implemented, not as a complete auditable training history.

Recommended runs are:

\begin{enumerate}
  \item baseline;
  \item candidate comparison;
  \item tuning/model selection;
  \item calibration and threshold policy;
  \item final holdout evaluation.
\end{enumerate}

Each should log dataset/schema versions, code revision, parameters, metrics,
artifact checksum, and the selected model/policy.

\section{Model threats to validity}

\begin{itemize}
  \item Metrics are saved artifacts and were not all independently regenerated
  during documentation.
  \item The local review environment initially lacked LightGBM.
  \item One validation window can favor a transient regime.
  \item V1/V2 feature sets differ.
  \item Operating-point metrics and calibration are missing.
  \item Full data is collected to pandas for fitting.
  \item No production shadow test or delayed-label drift study exists.
\end{itemize}

\section{Model-readiness decision}

V2 is the current software default and the saved offline champion. It should be
described as a rollback-safe candidate rather than a fully governed production
model until:

\begin{enumerate}
  \item a frozen environment loads and scores the artifact without heuristic
  fallback;
  \item operating-point and calibration evidence are produced;
  \item the backend policy uses an approved threshold contract;
  \item MLflow lineage and checksums are saved;
  \item shadow behavior and rollback are tested.
\end{enumerate}
