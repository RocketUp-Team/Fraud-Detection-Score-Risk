\section{Model-development protocol}

The training lifecycle follows the same boundary described in the architecture chapter: \textbf{Spark performs distributed data preparation, while Python estimators are fitted on a single node}. Figure~\ref{fig:final-training-lifecycle} illustrates how model-ready artifacts are loaded, candidate families are trained, validation metrics guide selection, calibration and thresholds are recorded, and the untouched holdout is used for final evidence. The workflow is reproducible at the level of contracts and saved metadata, although the single-node estimator stage remains a scalability boundary.

Model selection is intentionally performed before holdout evaluation. Candidate
families are fitted using the training contract, compared on the validation
window, and then subjected to calibration and operating-threshold decisions
that are also based on information available before the holdout. The holdout
is not used to tune hyperparameters or choose the winning family. This design
prevents the final metric from becoming another training signal and makes the
holdout result a more credible estimate of later-period behaviour. It also
explains why the report distinguishes validation selection metrics from
holdout operating metrics rather than presenting one undifferentiated score.

The comparison run uses \val{300} estimators or iterations for LightGBM,
XGBoost, and CatBoost, with project seed \val{42}; Logistic Regression uses
\texttt{max\_iter=1000}. The validation tuning grid evaluates \val{200} and
\val{400} estimators or iterations, tree depths \val{4} and \val{6}, and
learning rates \val{0.05} and \val{0.10} for the boosting families. LightGBM
is configured as deterministic and column-wise, XGBoost evaluates
\texttt{aucpr}, and CatBoost uses a fixed random seed. These settings describe
the implemented search space rather than claiming that every combination was
equally successful.

\section{PySpark MLlib DecisionTree baseline}

To satisfy the BDA501 big-data machine-learning requirement, a PySpark MLlib
\texttt{DecisionTreeClassifier} pipeline evaluates the \val{68}-feature vector
across original, weighted, and undersampled training variants. The results in
Table~\ref{tab:mllib-decision-tree} show the effect of imbalance treatment
clearly. The unweighted tree produces very low PR-AUC because it is dominated
by the majority class. Weighting increases recall and ranking quality
substantially, but precision falls because the model raises more alerts.
Undersampling changes the training distribution and improves neither ranking
quality nor generalisation enough to replace the weighted baseline.

training time, yet its PR-AUC remains close to the weak baseline.

\section{Candidate models and selection}

Evaluation compares Logistic Regression, LightGBM, XGBoost, and CatBoost under the same downstream contract, as shown in Table~\ref{tab:model-family-comparison}. CatBoost Balanced achieves the highest validation PR-AUC among the listed candidates, narrowly exceeding weighted LightGBM while also retaining a strong ROC-AUC. This result supports selecting CatBoost Balanced as the current challenger, but it does not by itself justify replacing the serving default because model promotion depends on the later holdout and governance gates.

The comparison also illustrates why model choice cannot be based on a single
metric or on model name. Logistic Regression provides a useful linear
reference but underperforms the boosting candidates on the nonlinear and
high-cardinality feature space. LightGBM and XGBoost provide strong ranking
baselines, while CatBoost Balanced obtains the best validation PR-AUC in the
recorded comparison. The selected candidate is therefore a result of the
observed contract-specific experiment, not a claim that CatBoost is always
superior for fraud detection. A different temporal window, sampling policy,
or feature contract could change the ordering.

\section{Current CatBoost candidate results}

Table~\ref{tab:official-v2-metrics} records the candidate across the validation and holdout windows. Validation results are used for model selection, while holdout results are treated as the more conservative estimate of performance on later data. The candidate reaches validation PR-AUC \val{0.5806} and ROC-AUC \val{0.9081}; on holdout, these decrease to \val{0.4266} and \val{0.8781}. The decrease is not evidence that the pipeline failed, but it is evidence that the candidate is sensitive to temporal shift and must be judged against the promotion threshold rather than the validation result alone.

At the selected holdout operating point, the candidate reports precision of
\val{0.3820} and recall of \val{0.5182}. In practical terms, the review queue
captures slightly more than half of the fraud cases represented by the
holdout while keeping the flagged set substantially smaller than the full
transaction population. The trade-off is not universally optimal: a bank with
high investigation capacity may prefer higher recall and tolerate more false
alerts, while a constrained team may require higher precision. The report
therefore treats the threshold as a policy decision that must remain visible
and configurable, rather than as a permanent property of the model weights.

\section{Packaging, checksum, and promotion}

The candidate promotion gate evaluates nine criteria, summarized in Table~\ref{tab:v2-gates}. The decisive failure is holdout PR-AUC: the observed \val{0.4266} is below the target \val{0.4582}. Although holdout ROC-AUC, review precision, calibration non-regression, checksum integrity, artifact loading, and data-contract checks pass, those successes do not override the failed ranking-quality gate. The candidate therefore remains \texttt{not\_promoted}, and the configured serving default is unchanged. This conservative decision keeps experimental performance claims separate from runtime behaviour.

The promotion state also demonstrates the value of separating technical
validity from model quality. A checksum match proves that the expected file
was loaded, but it does not prove that the model is good. A passing schema gate
proves that the feature vector is compatible, but it does not prove that the
candidate generalises. Conversely, a failed performance gate does not mean
that the data contract or serving package is broken. The promotion process
keeps these questions separate so that the team can improve the candidate or
revise the target without losing confidence in the integrity of the serving
default.

\section{Request-time scoring}

At request time, the scoring package maps categorical values using persisted indexers, applies the saved preprocessing and isotonic calibration state, and computes TreeSHAP feature attributions \parencite{lundberg2017shap}. The API supports both \texttt{full\_feature} and \texttt{partial\_demo} modes so that the demonstration can score complete model-ready records while still showing the user-interface flow for reduced examples. This packaging removes the need to start Spark for each request, but it also means that online feature construction must remain aligned with the offline contract if the system is ever deployed beyond the demonstration setting.
