\chapter{Validation and Whole-System Review}
\label{chap:validation}

\section{Validation strategy}

The review distinguishes five evidence states:

\begin{description}[style=multiline,leftmargin=4.2cm,labelwidth=3.9cm]
  \item[Verified now:] a command completed successfully during the documentation
  task.
  \item[Artifact-reported:] a value was read from a saved machine-readable
  artifact.
  \item[Previously validated:] a dated report records a successful prior run.
  \item[Implemented:] source code provides the capability but it was not
  exercised end to end.
  \item[Not evidenced:] neither a successful run nor adequate saved artifact was
  found.
\end{description}

This prevents the presence of a script or dependency from being reported as a
completed experiment.

\section{Processed-data validation}

The data verifier is the strongest machine-readable quality gate. It reports:

\begin{itemize}
  \item 82 checks passed and zero failed;
  \item model-ready datasets are non-empty;
  \item transaction identifiers are unique;
  \item labeled and unlabeled schemas use the expected target policy;
  \item class weights appear only in the weighted training variant;
  \item split order is chronological and split intersections are empty;
  \item manifest row counts and schema hashes match;
  \item feature order, medians, and required reports exist.
\end{itemize}

The stale \texttt{verification\_pending} value in the top-level manifest is a
finalization defect, not a failed data check, because the later verifier report
contains the terminal result.

\section{Static and runtime reports}

The dated static report records successful Python compilation, YAML/JSON
parsing, Compose configuration validation, leakage-pattern inspection, contract
artifact presence, and Docker build-context correction.

The runtime report records the failure/remediation history rather than only the
final pass:

\begin{enumerate}
  \item Windows Spark report paths conflicted with existing directories;
  \item Matplotlib attempted to use a GUI backend;
  \item Docker build context excluded required source;
  \item a long run left an incomplete/stale manifest;
  \item normalization and contract regeneration repaired the output;
  \item the verifier reached \texttt{ready\_for\_downstream\_training}.
\end{enumerate}

This history is valuable evidence because it documents why Docker Linux is the
canonical Parquet path and why the contract-finalization utility exists.

\section{Current dependency and execution constraints}

At the start of the review, the repository had no local backend/model virtual
environment or frontend \texttt{node\_modules}. The global Python environment
contained pandas, Joblib, and PyArrow but not LightGBM. Docker engine access was
also denied through the local named pipe.

These are environment constraints rather than direct source defects. They do,
however, demonstrate why a frozen container smoke is required before model
serving can be claimed independently reproducible.

\section{Threats to validity}

\subsection{Construct validity}

ROC-AUC and PR-AUC measure ranking, not business value. The saved results do not
establish fraud prevented, investigation effort, or customer impact.

\subsection{Internal validity}

V1 and V2 differ in feature count and preprocessing controls. Their comparison
cannot isolate the cause of improvement. A single validation window can also be
overfit by repeated model and parameter selection.

\subsection{External validity}

IEEE-CIS is anonymized historical competition data. Behavior, prevalence,
labels, feature availability, and latency constraints can differ from a live
merchant environment.

\subsection{Reproducibility}

Processed data is locally present and well contracted, but model artifacts are
Git-ignored. Five finished \texttt{0.0.2} runs are queryable in the local SQLite
store, but their artifact URIs are container-local and checksums, registry IDs,
promotion approval, and rollback records are absent.

\section{Production-readiness gates}

\subsection{Gate 1: reproducible serving}

\begin{enumerate}
  \item freeze dependencies;
  \item build the backend/model image;
  \item load V2 with the expected model version;
  \item score a full-feature holdout transaction without fallback;
  \item record image digest and model checksum.
\end{enumerate}

\subsection{Gate 2: approved operating policy}

\begin{enumerate}
  \item reproduce \texttt{0.0.2} calibration and threshold evidence on temporal
  windows not reused for model selection;
  \item compare its precision, recall, false positives, false negatives, and
  calibration with V2;
  \item define review capacity and error cost;
  \item approve, store, and enforce review/reject thresholds;
  \item test exact boundaries through model, backend, and UI.
\end{enumerate}

\subsection{Gate 3: operational controls}

\begin{enumerate}
  \item fail readiness when the expected model is unavailable;
  \item add structured logs, metrics, drift monitoring, and alerting;
  \item add migrations and durable job orchestration;
  \item add authentication, authorization, audit history, and secret management;
  \item add CI across data, model, backend, frontend, and full-stack smoke.
\end{enumerate}

\subsection{Gate 4: controlled promotion}

Run shadow scoring, compare paired predictions, approve the version with a
recorded decision, test rollback, and prevent mixed-version historical
statistics from being interpreted without a model-version filter or re-score.

\section{Overall assessment}

The system is successful against its academic demonstration objective. All
major layers exist and the data handoff is strongly verified. The gap to
production is not another dashboard page or another estimator. It is the set of
controls that makes an existing prediction trustworthy: reproducibility,
operating policy, lineage, readiness, security, and monitoring.
